# ONEOFF-RetireBdResidue 1.0.7

A **disposable** cleanup package. Install it, let it run, uninstall it.
It is **not** part of the shipped Bench Dogs package and must never become part of it.

Owner decision 🔒 1521: *"I wnat clean rep o and clean teannants give me a one off tha cleans the
tennants too"* — the retirement work moves out of `BenchDogs-Ext` and into this disposable
package, so the shipped package can carry only customer-category code (🔒 1508 / 🔒 1514 / 🔒 1520).

> **What changed in 1.0.7** (Rafael's delta review of Bench #41 at 98034ea5)
>
> * **N1:** the Bench Dogs version it requires is a literal in pack.php (`0.9.42-rc87`, the first release that
>   ships none of the listed paths). It changes only with a version bump of this one-off, and the build reads
>   nothing outside this package.
> * **N3:** step 1 sweeps `leftovers/custom/` only. The guarded subtrees sit beside it in `leftovers/if-bench/`, so
>   the unconditional sweep never walks them (§2 says why they stay inside `leftovers/`).
> * **N4:** each guarded subtree is named by its path (`leftovers/if-bench/<path>/<basename>`), not matched by
>   position. In 1.0.6, a list reordered between pack.php and post_execute deleted the wrong file in 4 of 6 orders.
> * The build refuses a listed path with a segment named `0`: Sugar's `dir_get_files` stops reading a directory
>   at such an entry (`while ($e = $d->read())`).
> * **N5/N2:** this README describes what the package does now; history is at the end. §3 says which tenants can
>   no longer run it.

> **What changed in 1.0.6** (Rafael's review of Bench #41; his one-off layout, as ONEOFF-RemoveErpLeftovers)

> * The zip is `scripts/post_execute.php`, `scripts/leftovers.php` and one placeholder per listed path under
>   `leftovers/`, generated by pack.php. There is no `lib/` or `leftovers/` in the source any more.
> * Everything listed is **DELETED** through Module Loader's `uninstall_new_files`; nothing is blanked, and
>   `emptied.php` is gone. A tenant that ran 1.0.4 or 1.0.5 has its blanked files deleted once.
> * The retired directories go through `uninstall_customizations`. K-2 and K-3 edit the deployed record views

> * New on the list: the pre-rc86 `custom/modules/Quotes/BdAdmRules.php`, and

## 1. The question that decided the design: does uninstall restore?

**Yes. Measured in SugarEnt-Full-26.1.0, not assumed.**

| step | file:line | what it does |
|---|---|---|
| `ModuleInstaller::install_copy()` | `ModuleInstall/ModuleInstaller.php:503-518` | takes `$backup_path = getBackupPath()` — `<installed zip path minus extension>-restore` — and calls `copy_path($from, $to, $backup_path)` |
| `copy_recursive_with_backup(..., $uninstall = false)` | `:2669-2678` | **`if (file_exists($dest)) { copy($dest, "$backup_path/$dest"); }`** then `copy($source, $dest)` |
| `ModuleInstaller::uninstall_copy()` | `:521-545` | recomputes the same backup path, calls `uninstall_new_files()`, then `copy_path($backup_path, $cp['to'], $backup_path, true)` |
| `copy_recursive_with_backup(..., $uninstall = true)` | `:2656-2662` | **`copy($source, $dest)` — the backed-up body is written back over the live path**, then the backup is unlinked |
| `uninstall_new_files()` | `:555-580` | deletes only files that have **no** backup, i.e. ones the package genuinely created |

So a one-off that shipped the retired paths **empty through `installdefs['copy']` would undo its own
work the moment anyone uninstalled it**, silently, on every tenant, while the install log still showed
it succeeding. That is strictly worse than doing nothing.

**This package therefore has no `copy` key in its manifest at all.** Every removal is performed from
`post_execute` by platform code. There is no copy list for `uninstall_copy()` to walk, no `-restore`
directory, and nothing to put back. **Uninstalling it is a genuine no-op** — the same property
`ONEOFF-RetireBdQuoteMirror` and `ONEOFF-DropBdQuoteMirrorTables` were built for.

*What it would look like if this were wrong:* `uninstall_copy()` would call only `uninstall_new_files()`
and never `copy_path(..., true)`, and `copy_recursive_with_backup()` would have no `$uninstall` branch.
Both are there, at the lines above.

### 🚩 The converse, and it is an operating rule

`BenchDogs-Ext` **does** ship every one of these paths through `copy`. Uninstalling *it* restores the
bodies that were on disk **immediately before that zip installed** — so uninstalling et's rc62 puts
back the **rc60-era** bodies, not rc62's. Said precisely because it is the sentence a reviewer will
check against `copy_recursive_with_backup():2669`: the backup is taken from `$dest` at install time.
The conclusion is unchanged and if anything worse: four of those rc60-era language files still
**declare** keys (measured: `en_us.bd_stage_doms.php`, `Accounts/en_us.bd_action_buttons.php`,
`Products/en_us.bd_line_order.php`, `Quotes/en_us.bd_action_buttons.php` all carry
`$app_list_strings`/`$mod_strings` assignments at `c4e8874`, and none do at rc66 `74a846e`).

> **Run this one-off after installing BenchDogs-Ext 0.9.42-rc87 or newer.** It is idempotent; re-running costs
> nothing. From 1.0.6 it **cannot** run once Bench Dogs is uninstalled (its manifest dependency is gone, §3), so
> bodies a Bench Dogs uninstall restores stay until Bench Dogs rc87+ is installed and this runs again.

Installing a *later* BenchDogs-Ext that no longer ships these paths does **not** resurrect them:
`install_copy()` only touches paths in its own copy list.

## 2. What it removes, and how

The worklist is `scripts/leftovers.php`: every path `BenchDogs-Ext` has ever installed under `custom/` that the
current release no longer ships. It is taken from the package's whole git history, not from its current tree,
because a census of the current package misses exactly the orphans Module Loader never deleted.
`tests/census.txt` holds the 136-path census the harness seeds a tenant from.

| list | what | how |
|---|---|---|
| `remove` | **111 files**: 87 `custom/Extension/` fragments (every retired `bd_*` vardef, label, hook registration, language fragment, and the accumulated `en_us.zz_bd_stage_doms.php`), plus 24 others: 22 retired class files, the REST stub `BdBenchDogsActionsApi.php` and the stage-dropdown template `custom/dropdowntemplates/bd_stage_doms.append.php` | **Deleted wherever present.** pack.php puts one placeholder per path under `leftovers/custom/…`. Step 1 calls `ModuleInstaller::uninstall_new_files(from = <package>/leftovers/custom, to = custom)`, which unlinks each matching instance path after a `file_exists`; it skips any path in `files.md5`, and none of these is. |
| `remove_if_bench` | **3 files other writers share**: the sales-stage style (4 Bench md5s, G599), the release-stage policy (8, G594), the order adapter (1) | **Deleted only when the file's md5 is a body Bench Dogs shipped.** Each comes from its own subtree, `leftovers/if-bench/<path>/<basename>` (`from` = that subtree, `to` = the path's directory), so one call reaches only its own file. The adapter stays while its planner `BdSubmitOrderPlan.php` still exists. Any other body is LEFT and reported under SKIPPED with its md5. |
| `directories` | **8**: `bd01_ERP_Quote`, `bd01_ERP_Quote_Line`, `bd01_ERP_Quote_Cost`, and the five retired `bd-*` button-field directories | `ModuleInstaller::uninstall_customizations()`, which removes `custom/modules/<name>`, `custom/Extension/modules/<name>` and `custom/working/modules/<name>`. Every entry is a Bench-only name. |
| K-2 | the retired Bench Dogs panel on the deployed Quotes record view | `ViewdefManager::loadViewdef('base', 'Quotes', 'record')`, the panel spliced out, then `saveViewdef` only when something changed |
| K-3 | the retired `bd_governing_origin` marker on the deployed Opportunities record view | the same, on Opportunities |

There is no cache call: `ModuleInstaller::install` runs its rebuild and repair after `post_execute`. Nothing is
blanked any more, so a file 1.0.4 or 1.0.5 blanked is on the `remove` list and is deleted once.

**Why the guarded subtrees are in `leftovers/if-bench/` and not literally beside `leftovers/`.** The
`check_built_packages` copy this repo vendors from erp-integration-sugar (G665) admits only `scripts/leftovers.php`
and `leftovers/` in a one-off zip; anything else is a member no installdef reaches. Step 1 sweeps
`leftovers/custom/` only, so the if-bench tree is beside the swept tree and is never walked by it.

**A listed path may not have a segment named `0`.** Sugar's `dir_get_files` reads a directory with
`while ($e = $d->read())`, and the string `"0"` ends that loop, silently skipping the rest of the directory.
pack.php refuses such a path. That loop is also why 1.0.6's whole-tree sweep happened not to list `if-bench/0/`.

## 3. Which tenants can run it, and in what order

The manifest requires `sugarai_benchdogs_ext` **>= 0.9.42-rc87**, the first release that ships none of the listed
paths. With an older Bench Dogs installed, some listed files are still that version's own, and Module Loader
refuses the install.

**So a tenant with Bench Dogs leftovers but no Bench Dogs package installed can no longer run it** (et, for
example). Module Loader refuses the dependency. Such a tenant keeps whatever earlier versions of this one-off
left, until Bench Dogs rc87 or newer is installed on it.

On a Bench Dogs tenant, the order is:
1. ERP-Epicor >= 1.2.0
2. Partial Fulfillment
3. Bench Dogs rc87 or newer
4. **this one-off**: read its Display Log, then uninstall it

## 4. Idempotency, and how an operator reads the result

Every entry is checked with `file_exists()` before and after. The report has these sections:
- **REMOVED**
- **ALREADY GONE**
- **SKIPPED** and **FAILED**: both mean the sweep is incomplete; read them.
- **NOT TOUCHED ON PURPOSE**

**A second run reports `REMOVED (0): NOTHING LEFT TO REMOVE.`**

The report goes to two places, neither of which is `sugarcrm.log`:

* **`echo`** goes to Module Loader's **"Display Log"** link on the install page. `ModuleInstaller::post_execute()`
  wraps the require in an output buffer that feeds `addInstallationMessage()`.
* **`$GLOBALS['log']->fatal()`** goes to `package_install.log`. For the duration of an install, `MlpLogger`
  points the default logger there at debug level. Export it from **Admin ▸ Diagnostic Tool** with only
  "Package Install Log" ticked. The line names the version that ran.

## 5. Build, test

CI builds this package with `php pack.php` and runs `php tests/harness.php`, through
`scripts/tests/test_oneoff_retire_bd_residue.py`. Both are linted in CI (🔒2155b).

The zip holds:
- `manifest.php`
- `scripts/post_execute.php`
- `scripts/leftovers.php`
- 114 placeholders: 111 under `leftovers/custom/` and 3 under `leftovers/if-bench/`. A `.php` placeholder is `<?php`, any other is empty.

`installdefs` holds only `post_execute`, with no `copy`.

The harness:
- runs the real pack.php in a temporary copy that has no `../BenchDogs-Ext`;
- unpacks the zip and runs its `post_execute` twice over a census-seeded tenant;
- uses SugarEnt 26.1's `uninstall_new_files`, `dir_get_files`, `dir_file_count` and `uninstall_customizations`, copied verbatim;
- runs one tenant per guarded case, and the guarded list in all six orders.
